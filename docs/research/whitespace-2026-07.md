## 2. THE ONE BEST BET

**Runtime mandate enforcement (#1).** It's the only direction scored 8, and it's foundational rather than optional: without it, Swale's entire pitch â€” Ed25519 "consume-once, time-bound, context-bound" mandates â€” is a *claim*, not a guarantee. A validly-signed mandate can still be replayed under a retry loop, raced by two concurrent workers, or redirected to a different merchant in a multi-hop orchestration. This direction closes that gap and makes everything else Swale says credible.

Why it wins the four-way test cleanly:
- **Unexplored & acknowledged-open**: three independent Q1â€“Q2 2026 papers name the exact gap; AP2 issue #118 shows even the mandate-*verification* flow is unstandardized.
- **Really real**: the mechanism is boring and proven â€” Stripe's idempotency-key pattern (unique-constraint + same-transaction insert) extended with an `H_ctx` context binding. Two measured prototypes report 100% replay interception vs. 0% for signature-only.
- **Non-custodial, solo-buildable**: the verifier touches no funds/keys/PANs; a single Postgres unique-constraint insert yields a correct v1. (Multi-region strong-consistency CAS is the hard 20% â€” a *scaling* concern, not a v1 blocker.)
- **Best thesis fit**: the nonce registry *is* the enforcement half of the audit ledger, and every consume/reject is a natural RFC 9162 transparency-log event.

Honest ceiling: it's a correctness primitive that makes the rest credible rather than a standalone category-definer, and it does **not** stop the confused-deputy/prompt-injection threat â€” market it as replay/concurrency/misapplication defense, never as intent-integrity. The competitive neighborhood (Skyfire, Nekuda, Payman, Catena, Mastercard Agent Pay) is well-funded, so the window is months, not years.

**First concrete step**: Build the atomic consume-once core as one Postgres table with a `UNIQUE(nonce)` constraint, and implement `verify()` as a single transaction that (1) checks Ed25519 sig, (2) checks TTL, (3) recomputes and compares `H_ctx`, (4) inserts the nonce â€” where a duplicate-key violation deterministically returns the *original stored decision*, not a new denial. Write the concurrency test first: fire two identical mandate-consume requests in parallel and assert exactly one settles and the second returns the first's verdict. That single test is the whole product's correctness proof â€” get it green before anything else.

Natural build order after that: #1 â†’ #7 (revocation reuses the same mandate lifecycle) â†’ #2 (witnessing hardens the log those events land in) â†’ #6/#4 (metering and cumulative analytics over the now-trustworthy event stream).

## 3. ALREADY TAKEN / NEEDS CUSTODY â€” do not chase

- **Reasoning-path transparency binding** â€” the one novel bit (self-reported reasoning digest) is audit-theater (signed â‰  caused the decision; CoT is unfaithful), bolted onto Microsoft's Agent Governance Toolkit, which already ships the non-reasoning govern-and-record stack.
